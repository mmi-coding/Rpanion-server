### Changelog
#### Unreleased (fork)
 - Feature (#398/#289/#9): **Multiple (secondary) video streams** — a new **Secondary Streams** page (under Camera & Video) runs extra video streams alongside the main camera, each a *different* camera on its own RTSP/RTP endpoint and its own `video-server.py` process (fault-isolated). The primary stream on the Photo & Video page keeps the full feature set (switcher / HUD / custom pipelines / recording / MAVLink protocol); secondaries are basic feeds (device, resolution, fps, bitrate, rotation, compression, transport). New `server/secondaryStreams.ts` (manager — add/remove/validate, **de-duplicated against the primary's live camera + other secondaries** so no camera is opened twice, capped at 3, restored on boot) + `server/routes/secondaryStreams.ts` (`/api/secondarystreams` + add/remove) + self-documenting `src/secondarystreams.jsx`. `video-server.py` gains `--rtsp-port` so secondary RTSP servers use a distinct port (`8555+slot`) instead of clashing with the primary's `:8554`. The UI surfaces the hardware reality (one camera per stream; two 1080p streams can saturate a Pi 4 / overwhelm a Zero 2 W). Both suites stay 100/100/100/100. See docs/reports/feature-34-secondary-streams.md.
 - Feature (#311): **Multiple serial telemetry links** — the Flight Controller page can now connect to several MAVLink telemetry sources at once (UART and/or UDP) and route them all to the ground station, which tells the vehicles apart by system id. Each link is **independent**: its own `mavlink-routerd` + its own connection monitor (the single-vehicle `mavManager` reused per link), so one link dropping out doesn't affect the others (fault isolation), and each shows a full live **status card** (connection, packets, vehicle, firmware, position) with a Remove button. New `server/fcLink.ts` (`FCLink`, one link's lifecycle) + a rewritten `flightController.ts` orchestrator (add/remove/validate/de-dup, capped at 4 links, MAVLink fan-out for RTCM/camera/heartbeat to every vehicle) + new routes (`/api/FCAddLink`, `/api/FCRemoveLink`, `/api/FCOptions` replacing `/api/FCModify`) + a rewritten, self-documenting `src/flightcontroller.jsx` (add-link form + per-link cards). The shared UDP-client destinations carry every vehicle; the bind-once UDP-Server/TCP-Server outputs + DataFlash logging follow the first link (documented). An existing single-link config is auto-migrated to a one-element links list, so current setups keep working. Both suites stay 100/100/100/100. See docs/reports/feature-33-multi-serial-telemetry.md.
 - Fix (#224): Ship the **`timedatectl set-timezone` sudoers grant** in `debian/postinst` so the Time Zone page works on-device. The POST runs `sudo timedatectl set-timezone <zone>`, which the rpanion service user could not run password-less until now (it had only been *noted* as a manual step). It is now granted automatically on install/redeploy, alongside the existing `shutdown`/networking grants. Found while verifying #224 on the Pi.
 - Feature (#173): **Telemetry HUD overlay on the video stream** — an optional, burned-in text readout (altitude · ground speed · heading · battery V/% · flight mode · GPS fix/sats) drawn onto the video itself, so any viewer or recording sees it, not just a ground station with its own MAVLink link. A new **Telemetry HUD** checkbox on the Video page enables it. Live telemetry is captured in `videostream.ts`'s existing `onMavPacket` tap (`VFR_HUD`/`SYS_STATUS`/`GPS_RAW_INT`/`HEARTBEAT`) and pushed ~5 Hz to the video server over the existing stdin control channel (`{"cmd":"hud",…}`); `video-server.py` inserts a `textoverlay name=hud0` into the raw-video section (single / dual-source / multi-RTSP pipelines) and updates its text live. Text + ArduPilot copter/plane/rover mode-name mapping live in a new pure, fully-tested `server/hudOverlay.ts`. Like the timestamp, the overlay is drawn before encoding, so it applies to CSI / MJPEG / raw sources the box re-encodes — **not** pre-compressed H264 or RTSP passthrough (the UI disables the toggle and explains why). No new system dependency (`textoverlay` ships with the same plugins as the existing `clockoverlay`). A graphical artificial-horizon HUD is a documented follow-up. Both suites stay 100/100/100/100. See docs/reports/feature-32-hud-overlay.md.
 - Feature (#224): **Set the system time zone from the web UI** — the About page gains a "Time Zone" section: a `<Form.Select>` of every IANA zone (`Intl.supportedValuesOf('timeZone')`) defaulting to the current zone, and a **Set Time Zone** button (enabled only when a different zone is picked).  - VPN: New **WireGuard Hub** page (`/wireguardhub`) — a turnkey generator for a self-hosted WireGuard rendezvous server. The user enters their VPS public IP, a domain/subdomain, and a few defaults (UDP port, VPN subnet, SSH port); the page emits a single self-contained bash script to run once on a fresh VPS (`sudo bash setup-wireguard-hub.sh`). The script installs WireGuard, enables IP forwarding + NAT, opens only the SSH + WireGuard UDP ports (ufw, SSH-safe), generates all keys **on the VPS** (none ever touch the companion computer), and prints ready-to-use `pi.conf` (upload on the VPN page) and `laptop.conf` (import on the ground station) — split-tunnel with `PersistentKeepalive`, `Endpoint` set to the domain. To get the script *onto* the VPS, the page shows ready-to-run `scp`/`ssh` deploy commands with the VPS IP + SSH port pre-filled (plus a no-save `ssh … 'bash -s' < …` one-liner). To get the configs back *off* the (remote, USB-less) VPS, the script prints ready-to-run `scp` commands and, when run via `sudo`, drops login-user-owned copies so scp needs no root SSH login. Solves the CGNAT problem for plain WireGuard (the drone can't accept inbound, so both ends dial out to the hub). New `server/wireguardHub.js` (pure generator) + `server/routes/wireguardHub.js` (`POST /api/wireguardhubscript`, strict IP/FQDN/port/CIDR validation since inputs are interpolated into bash) + `src/wireguardhub.jsx` (self-documenting: HelpTips + HelpSection).
